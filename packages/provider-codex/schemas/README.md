743 and 888 files generated by the audited npm `@openai/codex@0.162.1` binary

All 743 stable files were compared byte-for-byte with
https://github.com/openai/codex/tree/rust-v0.162.1/codex-rs/app-server-protocol/schema/typescript
and matched. The deterministic recording is
`tests/fixtures/codex-0.162.1-schemas.json.gz`, under the same Apache-2.0 license.

Compared with 0.160.1, stable adds 9 files and changes 21; experimental adds 13
and changes 23. Neither removes files. Changes include partial-answer message
phase, turn ancestry, subagent model/effort metadata, attachment owner listing,
browser extension headers, independent speed requirements, misalignment error

Approval responses, sandbox policy contracts and initialize remain unchanged.
Additional metadata does not authorize tools or grant execution capabilities.

Both full closures must match the same reviewed protocol before the existing
handshake and effective-policy probes run. This also permits a newer executable
with an identical protocol, without granting it another version's native safety
evidence. Protocol compatibility and native execution certification are separate.

Process inspection (`ps`) is denied here. These results do not certify native

### Follow-up diagnosis (2026-10-19)

Both 0.160.1 and 0.162.1 were installed under separate `.scratch` prefixes after
`dep check`; neither machine installation was replaced. Source archives for `rust-v0.160.1` and `rust-v0.162.1`, and release notes
for `rust-v0.161.0`, `rust-v0.162.0` and `rust-v0.162.1`, were inspected. The 0.162.1 release fixes multiline TUI questions and background
server feature compatibility. Neither fix renames native approval events.

The exported `ServerRequest`, command/file approval parameters and responses,
`CommandExecParams`, `ThreadStartParams` and `ThreadResumeParams` are byte-identical
between the recorded experimental closures. The config schema entries for
`approval_policy`, `approvals_reviewer`, `sandbox_mode`,
`sandbox_workspace_write`, `default_permissions`, `permissions`,
`allow_login_shell` and `shell_environment_policy`, plus all approval, filesystem,
network and permission-profile definitions, are structurally identical. App-server
CLI help is identical. Sandbox help only adds Windows uninstall/help subcommands
and changes the usage presentation; existing permission-profile flags are unchanged.
There is no evidence that these failures require different provider flags or keys.

The original replay's synthetic SQLite event history records
`run.failed` with `reason: process_probe_unavailable`, an empty process inventory
and input `delivery_unknown`. `RpcPeer.start` requires process identity before
returning to the replay adapter, so this run never reaches initialize, turn/start
or native approval dispatch. Waiting for an approval concealed that earlier
failure. The replay now detects this terminal failure and reports its controlled
identifier immediately, while retaining every allow/deny/effect/delivery assertion.

For confinement, scratch-only diagnostic instrumentation captured the full
`command/exec` error for **both versions**:
`-32603: exec failed: unsupported operation: Operation not permitted (os error 1)`.
There was no command exit code: this is an RPC execution failure, not a successful
command whose filesystem access was denied. Independently, `/bin/ps` is denied
by the worker and a restrictive `sandbox-exec` invocation fails with
`sandbox_apply: Operation not permitted`. The confinement probe now distinguishes
RPC failures from exit-code/effect failures without retaining raw CLI diagnostics
or weakening any assertion. Both versions still fail in this restricted worker.

Consequently 0.162.1 remains disabled. No provider policy was loosened or safety
evidence promoted. Successful native proofs require a validation environment where
the existing process-identity and native sandbox operations are permitted. Live
inference turns in this follow-up: zero.

### Native proofs outside the worker sandbox (2026-10-19)

Both probes were repeated where process inspection and the native sandbox are
permitted. The 0.160.1 baseline passed all eight native replay checks and all
twelve confinement checks there, so the environment is sound.

0.162.1 passed all twelve confinement checks, identical to 0.160.1; the earlier
confinement failure came from the restricted worker. The native replay fails
`approval_effect_mismatch` on its approved command: the approval is delivered and
accepted, the command runs and exits 1 with `operation not permitted` writing a
marker in its own workspace. With the approval check reported instead of thrown,
the other seven replay checks pass (deny, question, built-in reader, exact resume,
delegation, interrupt, detached cleanup). 0.163.0 behaves the same.

Cause, from the `rust-v0.162.1` source (#49353, first released in 0.161.0): an
approved `require_escalated` command now gets a wider filesystem policy when the
profile has denied paths. `FileSystemSandboxPolicy::for_approved_command` builds a new
policy of root write plus the baseline's `deny` entries only, dropping the
workspace write entry. The node places workspaces under its state directory, which
the profile denies, so an approved command loses write access to its own
workspace. (Correction: 0.160.1 does not run such a command unsandboxed either. With
deny entries in the profile it falls back to the ordinary profile, so an approved
command there writes only inside the workspace. 0.161+ instead lets it write
anywhere that is not denied, which is wider.)

0.162.1 and 0.163.0 stay disabled. Enabling them needs a policy decision (where
workspaces live relative to denied paths, or how escalation requests are answered),
not new evidence strings. 0.163.0 also fails both schema pin sets
(`codex_schema_fingerprint_mismatch`) and needs its own protocol review. Live
inference turns: zero.

### 0.162.1 enabled (2026-10-19)

An approved escalation on 0.162.1 is kept to the ordinary profile, exactly as on
0.160.1: the profile denies the filesystem root `/` explicitly. Most specific entries
win, so the workspace write, the read grants and the other denies are unchanged for
ordinary commands. `for_approved_command` returns the ordinary profile unchanged when
the root is not writable under the widened policy, so an approved command writes only
inside the workspace, `.git` and `.codex` stay read-only, and node state, the
workspace's parent folder, the Codex home and temp folders stay denied as whole
directories. An earlier attempt on this branch denied ancestors as "everything beside
the workspace" globs; review showed it left approved commands writing anywhere else
and `.git` writable, and it was replaced by this.

Outside the worker sandbox both probes pass fully on 0.160.1 and 0.162.1. The replay
probe now also proves that an approved escalation cannot read node state or a
neighbouring worktree, cannot write into state or outside the workspace, cannot write
`.git` or `.codex` in a registered repository, and cannot move, remove or replace
any directory from node state down to the workspace (including moving the workspace
out and linking its path into state). Any such exposure fails the probe on every
version. The confinement probe has 19 checks. 0.162.1 is enabled on its own evidence.
0.163.0 stays disabled: its schemas match neither reviewed protocol and it needs its
own protocol review. Live inference turns: zero.

Git metadata in every layout: the provider resolves both the common dir and the gitdir
(`git rev-parse --git-common-dir --absolute-git-dir`) and marks each read-only inside
the workspace or denied outside it, besides `<workspace>/.git`. Before this, a common
dir inside the workspace under another name had no entry, and a worktree's gitdir was
covered only through the common dir. The replay probe now runs ordinary and approved
writes to the gitfile, common `config` and hooks, and gitdir `HEAD` and
`config.worktree` for a node-created worktree and for a worktree of a repository
nested inside it; all are refused on 0.160.1 and 0.162.1. A `--separate-git-dir`
checkout is not offered as an execution target by the node, so it cannot reach Codex.
